# SeaweedFS storage spike (CTO-03)

[IMPLEMENTED] CTO-03 and endy-rkt-03 evaluated SeaweedFS as the local S3-compatible object store for D05. This page records the environment, the checks, the findings and the limits. The setup itself is INFRA-01, in the [root Compose file](../../docker-compose.yml) and [data and storage](data-storage.md#s3-compatible-option). Run 2026-11-22.

## Scope

Validate the checks D05 asks for before media delivery can be closed: put and get, private access, scoped identities, ranged reads, deletion, restart persistence, and representative video and 3D asset sizes.

Out of scope: load and concurrency testing, TLS, multipart transfers, codec playback, malware scanning, and managed object storage.

## Environment

- `chrislusf/seaweedfs:4.54`, single node, S3 gateway on port 8333, Compose service `seaweedfs`.
- Docker 29.9.2 on Linux, Compose project `lova`, network `lova_internal_net` (internal, no egress).
- Client: the `amazon/aws-cli` image on the same network with `--endpoint-url http://seaweedfs:8333`. The service publishes no port; clients must run inside the Compose network.
- Assets: a 12 MiB image-sized file, a 50 MiB video-sized file and a 5 MiB GLB-sized file, filled with random bytes. SHA-256 was compared after every round trip.
- Credentials come from the root `.env` generated by `npm run setup:env`. No key or token is printed here or committed.

## Findings

### 1. Restart crash loop in `start.sh` (fixed)

`docker compose restart seaweedfs` entered a crash loop:

```
/etc/lova/start.sh: line 14: can't create /tmp/lova-s3.json: Permission denied
```

The image entrypoint re-executes itself as the unprivileged `seaweed` user. The first start created `/tmp/lova-s3.json` as root; on restart the script ran as `seaweed`, and the sticky `/tmp` refused to truncate the root-owned `0600` file, so `set -eu` exited 1 and the restart policy repeated it. Every run since INFRA-01 used `docker compose up`, which gives a fresh container filesystem, so the defect had not surfaced.

The fix renders the config to a file created per run:

```sh
config="$(mktemp /tmp/lova-s3.XXXXXX)"
```

`mktemp` always creates a file owned by the current user, so either user context can write it. BusyBox `mktemp` requires the template to end with `XXXXXX`, so the file has no extension. Verified with two consecutive `docker compose restart` runs: healthy, object still readable, identical SHA-256, and no `Permission denied` line in the log.

### 2. No filer or STS signing key (open)

The S3 gateway logs, three times across the runs:

```
Failed to load IAM configuration: no signing key found for STS service;
please provide 'signingKey' in IAM config, configure 'jwt.filer_signing.key'
in security.toml, or ensure SSE-S3 is initialized
```

The bucket policies rendered from the root `.env` are still enforced: the scoping and anonymous checks above fail closed. What is missing is the STS/IAM signing key, which leaves the filer IAM gRPC service unauthenticated to anything else on `internal_net`. [DECISION REQUIRED: endy-rkt] Add a `security.toml` with `jwt.filer_signing.key` from a root `.env` secret generated by `setup:env`. This spike does not change it: it is shared infrastructure owned by endy-rkt, and the key source needs approval. It is not a blocker for a single-host demo behind the internal network, but it should be closed before anything else can join that network.

### 3. Free disk headroom is a hard requirement (open, operational)

With the host filesystem at 100% (422 MB free), every write failed:

```
No writable volumes and no free volumes left
create 7 volume, created 0: Not enough data nodes found!
```

SeaweedFS marked its only volume `ReadOnly` and the S3 gateway answered `InternalError`. After freeing 11 GB the same writes passed. The demo host and any CI runner need several GB of headroom, or uploads fail with an opaque error that points at the client rather than at storage.

### 4. First write is slow (warming)

The first 12 MiB write on a fresh cluster took 26.9 s while the first collection volume was allocated; later writes took 1.4 s (5 MiB) and 3.3 s (50 MiB). Warm the stack with one throwaway upload before rehearsal (DEMO-01, DEMO-04) so the first real contribution does not stall.

## Recommendation

SeaweedFS 4.54 on a single node satisfies the D05 checks: private buckets, per-service identities, ranged reads, deletion and restart persistence all hold, and the representative sizes transfer in seconds on local storage. Keep gateway-mediated delivery, private buckets, one bucket per writing service and a persistent volume.

CTO-04 can close D05 once the signing-key and disk-headroom conditions are accepted as operational requirements.

## Reproduction

```sh
npm run setup:env
docker compose up -d seaweedfs seaweedfs-buckets
# Then, from a container on lova_internal_net, with the root .env credentials:
#   aws s3api --endpoint-url http://seaweedfs:8333 put-object ...
#   aws s3api --endpoint-url http://seaweedfs:8333 get-object --range bytes=0-1023 ...
docker compose restart seaweedfs
```

## Limits

- One node, one host and a local filesystem: no replication, no erasure coding and no measured concurrency.
- No TLS, no presigned URLs and no multipart upload above the SDK threshold were exercised.
- Random bytes are representative of size only; no real image, video or GLB was decoded from storage.
- Measurements come from one session on a shared machine and are indicative, not a benchmark.
