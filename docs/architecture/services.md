[RECOMMENDED] **NFT and Content handoff.** Agree on an opaque content ID, publication eligibility, the attribution and evidence fields NFT may copy into its public snapshot, and the behavior when an item is edited or unpublished. Existing token metadata should describe the approved snapshot and the scope of the recorded event.

[RECOMMENDED] **LiDAR and Content handoff.** Confirm the content ID with Content before association. LiDAR owns asset status. The gateway can look up a published item's 3D association through LiDAR using its content ID. Keep credentials and object keys internal and return only approved delivery references.

## Dockerfile placement

[CONFIRMED] Each app or service owner writes its Dockerfile in its own directory and adds its entry to root `docker-compose.yml`. Use `apps/frontend/Dockerfile` and one `apps/backend/<service>/Dockerfile` each for gateway, Auth, Content & Verification, NFT and LiDAR. Coordinate Compose edits and verify the service starts with its declared dependencies once Docker setup is available. Reserve `infrastructure/docker/` for non-service configuration. [Ownership rules](../team/responsibilities.md#task-ownership)

[CONFIRMED] Use repository-root context (`context: .` in root Compose) when the build needs `packages/shared`, the root npm lockfile or any other repository-root input. For example, set `dockerfile: apps/backend/<service>/Dockerfile` with that context. Use an app-local context only if all required inputs are app-local, with `dockerfile: Dockerfile` relative to that directory. [Compose build path resolution](https://docs.docker.com/reference/compose-file/build/)

For root-context builds, use `Dockerfile.dockerignore` beside the Dockerfile. It takes precedence over the root `.dockerignore`, so include all required exclusions there. For app-local builds, use `.dockerignore` in the app directory. In either case explicitly exclude local env files, credentials, VCS data and local artifacts while retaining declared build inputs. Build each image independently and include only the target application's runtime artifacts and dependencies. Test every dependent workspace when a shared input changes and include each dependent image in the Docker CI rebuild scope once that check is available. [Docker ignore-file behavior](https://docs.docker.com/build/concepts/context/)

[CONFIRMED] Run every `npm ci` step with a shared BuildKit cache mount: `RUN --mount=type=cache,id=npm,target=/root/.npm npm ci --prefer-offline ...`, in a stage that runs as root. All service builds share the `npm` cache ID, so a package downloaded once serves every image and rebuild, including after a `COPY . .` invalidates the install layer. Start each Dockerfile with `# syntax=docker/dockerfile:1`. Run `docker builder prune --filter type=exec.cachemount` to clear the cache. [BuildKit cache mounts](https://docs.docker.com/build/cache/optimize/#use-cache-mounts)

## Contracts and shared package

[CONFIRMED] Each API producer owns its OpenAPI document in [docs/api](../api/). endy-rkt owns the public gateway contract and system-wide conventions. Producers agree changes with affected consumers, favor backward-compatible changes and verify contracts at integration boundaries. The frontend accesses application APIs through the gateway. [D14 decision record](../decisions/project-decisions.md#d14-shared-contracts-and-build-context)

Start with producer-owned contracts. Introduce `packages/shared` only when multiple consumers need the same transport declarations. Permit type-only imports of transport declarations, including generated types and any common error type. Keep runtime validators, clients, business logic and persistence models with their owning applications.

The public gateway contract documents stable error codes, a safe message and a request ID. The gateway maps upstream timeouts and unavailable services to appropriate public statuses. Test those mappings and verify that public responses omit internal exception details, credentials and personal data.
